P1-02【并发】没有任何单实例锁，--once 与 --loop 争同一个库：这就是 exit=124 的根因（任务单 §三-1）
位置：
全仓没有 flock/fcntl/pidfile。grep 只命中 daily_check.py:822，它只是展示 pid 文件。
crawler/main.py 没有 --once（参数定义在 :120-160，argparse 会直接以 2 退出）。
带 --once 的入口是：indicators/run.py:101、sources/jev.py:668、execution/run.py:51、decision_engine/run.py:79、sources/news.py:461、sources/ccxt/run.py:33。
checkpoint 无属主、无租约：store.py:650-663；one-shot 运行可以接管 loop 正在进行的 cycle：pipeline.py:647-651、:682-688。
main.py:188-193 收到 SIGTERM 只设置 stop 标志；pipeline.py:575 在 gather 期间不检查这个标志（只在 :536 和 :581 检查）。
触发条件： 任一入口的 --once 与它自己的 --loop 同时运行，例如 timeout N python -m indicators.run --once；或 main.py 的一次性运行与 loop 同跑。
影响：
exit 124 的含义： 这是 GNU timeout 自己的超时退出码，不是程序的退出码。
一次性运行为什么会超时：
打开 Store() 就要等写锁（见 P1-03）。
每次提交都要争锁。IndicatorStore、JevStore、SignalBus 的 busy_timeout 只有 5 s。
单次工作量没有上限（现网 pending 13,750 个）。
SIGTERM 要等 C 层等锁返回后才被处理。
用 timeout 时没有加 -k，不会补发 SIGKILL。
其他后果： execution.run --once 与 --loop 会重复消费同一批 decision_log（见 P1-04）。main.py 的一次性运行会接管或提前结束 loop 的 checkpoint，并造成重复 enrich 与重复告警。
复现（主审实跑）： 另一个连接持有 BEGIN IMMEDIATE 时，执行 timeout 3 python -c "Store(db)"，结果 exit=124。子审查另测了 main.py --skip-lists 的同一场景，结果为 exit=124，耗时 19.99 s，SIGTERM 之后日志仍打出 "Cycle completed successfully"。
修复建议：
每个常驻入口启动时先 fcntl.flock(open(f"logs/{name}.lock","w"), LOCK_EX|LOCK_NB)。--once 拿不到锁就以 75 退出，或改为给 loop 投递一个"立即跑一轮"的标志。
checkpoint 增加 owner 与 lease_until，更新时 WHERE 带上 owner。
fetch_one 内部检查 stop 标志，stop 时取消剩余任务；每轮设置批次上限。
运维上统一用 timeout -k 10 …。
